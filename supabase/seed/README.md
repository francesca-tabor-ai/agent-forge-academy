# Seed Data Workflow

This directory contains seed scripts to populate the database with initial data for development and testing.

## Seed Scripts

Run scripts in this order (following dependency order):

1. **`00_reset.sql`** (Optional) - Resets seed data by truncating tables
2. **`01_seed_core.sql`** - Seeds core data: subscription plans (no dependencies)
3. **`02_seed_content.sql`** - Seeds content: courses (no dependencies)
4. **`03_seed_events.sql`** - Seeds events: demo days, workshops, networking events (no dependencies)
5. **`04_seed_jobs_offers.sql`** - Seeds jobs and offers: job listings and tool discounts (no dependencies)
6. **`05_seed_user_dependent.sql`** - Example queries for user-dependent data (requires existing profiles/student_profiles)
7. **`07_seed_advisor_context.sql`** - Seeds advisor context: active course/project/job context for students (requires existing student_profiles)
8. **`08_seed_advisor_conversations.sql`** - Seeds advisor conversations: conversation history for students (requires existing student_profiles)
9. **`09_seed_answers.sql`** - Seeds answers: answers to questions from students and tutors (requires existing questions and profiles)
10. **`10_seed_consent_events.sql`** - Seeds consent events: audit trail for visibility changes and contact approvals (requires existing student_profiles, portfolio_projects, contact_requests)
11. **`11_seed_contact_requests.sql`** - Seeds contact requests: requests from recruiters to students (requires existing recruiter_profiles and student_profiles)
12. **`12_seed_course_enrollments.sql`** - Seeds course enrollments: student enrollments in courses (requires existing courses and student_profiles)
13. **`13_seed_course_redirects.sql`** - Seeds course redirects: redirects for renamed or merged courses (requires existing courses)
14. **`14_seed_email_outbox.sql`** - Seeds email outbox: email queue for weekly learning and jobs emails (requires existing student_profiles)
15. **`15_seed_event_attendance.sql`** - Seeds event attendance: RSVP and attendance records for events (requires existing events and profiles)
16. **`16_seed_event_presentations.sql`** - Seeds event presentations: links students to projects they're presenting at events (requires existing events, student_profiles, and portfolio_projects)
17. **`17_seed_lesson_chunks.sql`** - Seeds lesson chunks: chunked lesson content for RAG (requires existing courses)
18. **`18_seed_lesson_progress.sql`** - Seeds lesson progress: individual lesson progress tracking for students (requires existing courses and student_profiles)
19. **`19_seed_offer_claims.sql`** - Seeds offer claims: student claims for tool discounts and offers (requires existing offers and student_profiles)
20. **`20_seed_payments.sql`** - Seeds payments: payment history ledger (requires existing auth.users, optionally subscriptions)
21. **`99_verify.sql`** - Verification script to check seed data integrity

## Dependency Order

The seed scripts follow this dependency order based on foreign key relationships:

### Independent Tables (Can be seeded first)
- `subscription_plans` - No dependencies
- `courses` - No dependencies
- `events` - No dependencies
- `jobs` - No dependencies
- `offers` - No dependencies

### Content-Dependent Tables (Require existing courses)
- `lesson_chunks` - Depends on `courses` (course_slug references)

### User-Dependent Tables (Require existing auth.users/profiles)
These tables cannot be seeded without existing user accounts:

1. **profiles** - Depends on `auth.users` (created via authentication)
2. **student_profiles** - Depends on `profiles`
3. **recruiter_profiles** - Depends on `profiles`
4. **portfolio_projects** - Depends on `student_profiles`
5. **course_enrollments** - Depends on `courses` + `student_profiles`
6. **questions** - Depends on `student_profiles`
7. **answers** - Depends on `questions` + `profiles`
8. **event_presentations** - Depends on `events` + `student_profiles` + `portfolio_projects`
9. **event_attendance** - Depends on `events` + `profiles`
10. **contact_requests** - Depends on `recruiter_profiles` + `student_profiles`
11. **advisor_context** - Depends on `student_profiles` + `courses` + `jobs` + `portfolio_projects`
12. **advisor_conversations** - Depends on `student_profiles` + `courses` + `jobs` + `portfolio_projects`
13. **answers** - Depends on `questions` + `profiles` (students and tutors)
14. **consent_events** - Depends on `student_profiles` + `portfolio_projects` + `contact_requests` (typically auto-generated by triggers)
15. **course_enrollments** - Depends on `courses` + `student_profiles`
16. **course_redirects** - Depends on `courses` (typically created when courses are renamed or merged)
17. **email_outbox** - Depends on `student_profiles` (typically auto-generated by cron jobs)
18. **lesson_progress** - Depends on `courses` + `student_profiles`
19. **offer_claims** - Depends on `offers` + `student_profiles` (optional: portfolio_projects)
20. **payments** - Depends on `auth.users` (optional: subscriptions, stripe_customers)

### Auto-Generated Tables (Created by triggers, cron jobs, or webhooks)
- `consent_events` - Auto-generated by triggers on visibility changes and contact approvals (seed file available for historical data)
- `admin_audit_log` - Auto-generated by triggers on admin actions
- `email_outbox` - Auto-generated by cron jobs (weekly-learning-emails, weekly-jobs-emails) (seed file available for testing)
- `payments` - Auto-generated by Stripe webhooks (invoice.paid events) (seed file available for testing)

**Note:** `05_seed_user_dependent.sql` contains example queries (commented out) that you can uncomment and run after users have signed up and profiles exist.

## Usage

### Using the run-seeds.sh script (Recommended)

```bash
# Run all seed scripts
./scripts/run-seeds.sh

# Run with reset (clears existing seed data first)
./scripts/run-seeds.sh --reset
```

```bash

export $(grep -v '^#' .env | xargs)

# Run each script in order
psql "$SUPABASE_DB_URL" -f supabase/seed/01_seed_core.sql
```

## Schema Discovery

Before creating or updating seed scripts, you can discover the actual database schema to ensure accuracy:

```bash
# Run the schema discovery script
./scripts/discover-schema.sh
```

This will generate `supabase/seed/SCHEMA_DISCOVERY.md` with:
- All tables and columns with their data types
- Foreign key relationships (to understand seeding order)

Alternatively, you can run the queries manually:

```bash
# Discover all columns
psql "$SUPABASE_DB_URL" -c "
select table_name, column_name, data_type, is_nullable
from information_schema.columns
where table_schema='public'
order by table_name, ordinal_position;
"

# Discover foreign keys
psql "$SUPABASE_DB_URL" -c "
select
  tc.table_name,
  kcu.column_name,
  ccu.table_name as references_table,
  ccu.column_name as references_column
from information_schema.table_constraints tc
join information_schema.key_column_usage kcu
  on tc.constraint_name = kcu.constraint_name
join information_schema.constraint_column_usage ccu
  on ccu.constraint_name = tc.constraint_name
where tc.constraint_type = 'FOREIGN KEY'
  and tc.table_schema = 'public'
order by tc.table_name;
"
```

## Seed Strategy: Hardcoded Deterministic UUIDs

All seed scripts use **hardcoded UUID strings** for deterministic IDs. This ensures:

- ✅ **Consistent IDs**: Same records always get the same UUID across runs
- ✅ **Easy References**: Other scripts can reference parent records by hardcoded UUID
- ✅ **Idempotent**: Safe to re-run - `ON CONFLICT` handles updates gracefully
- ✅ **Works in Supabase**: No dependencies on extensions - works everywhere
- ✅ **Simple**: No helper functions needed - just use the UUID string directly

### UUID Ranges

Each table type uses a distinct UUID prefix for easy identification:

- **Courses**: `a1b2c3d4-e5f6-4789-a012-3456789abc01` through `a1b2c3d4-e5f6-4789-a012-3456789abc14`
  - Example: Multi-Agent Systems = `a1b2c3d4-e5f6-4789-a012-3456789abc06`
  
- **Events**: `b1b2c3d4-e5f6-4789-a012-3456789abc01` through `b1b2c3d4-e5f6-4789-a012-3456789abc15` (15 events)
  - Example: Q1 2025 Demo Day = `b1b2c3d4-e5f6-4789-a012-3456789abc01`
  
- **Jobs**: `c1b2c3d4-e5f6-4789-a012-3456789abc01` through `c1b2c3d4-e5f6-4789-a012-3456789abc25` (25 jobs)
  - Example: AI Engineer - TechCorp AI = `c1b2c3d4-e5f6-4789-a012-3456789abc01`
  
- **Offers**: `d1b2c3d4-e5f6-4789-a012-3456789abc01` through `d1b2c3d4-e5f6-4789-a012-3456789abc20` (20 offers)
  - Example: Supabase Pro offer = `d1b2c3d4-e5f6-4789-a012-3456789abc01`

### Referencing Parent Records

```sql
-- In user-dependent seed scripts, reference courses/events by hardcoded UUID:
DO $$
DECLARE
  course_id_var UUID := 'a1b2c3d4-e5f6-4789-a012-3456789abc06'::uuid; -- Multi-Agent Systems
BEGIN
  INSERT INTO course_enrollments (course_id, student_profile_id, progress_percentage)
  SELECT course_id_var, sp.id, 0
  FROM student_profiles sp
  LIMIT 10;
END $$;
```

## Row Level Security (RLS) and Seeding

**Important**: Seed scripts must bypass RLS to insert data into tables with RLS enabled.

### Recommended Approach: Direct Database Connection

The seed scripts use **direct database connection strings** (via `psql`), which automatically bypass RLS:

- ✅ **Direct Connection**: `postgresql://postgres:[PASSWORD]@[HOST]:5432/postgres`
- ✅ **Transaction Pooler**: `postgresql://postgres.[PROJECT]:[PASSWORD]@[HOST]:5432/postgres`

When you connect via `psql` using the direct database connection string, you're connecting directly to PostgreSQL (not through PostgREST), which bypasses RLS automatically.

### How It Works

1. **Get Connection String**: 
   - Supabase Dashboard → Project Settings → Database
   - Copy "Direct connection" or "Transaction pooler" connection string
   - Add to `.env` as `SUPABASE_DB_URL`

2. **Run Seeds**:
   ```bash
   ./scripts/run-seeds.sh
   ```
   The script uses `psql` with the direct connection string, which bypasses RLS.

3. **Why This Works**:
   - Direct PostgreSQL connections don't go through PostgREST
   - RLS policies only apply to PostgREST API requests
   - `psql` connects as the database user, not an application user

### Alternative: Service Role (Not Recommended for Seeding)

If you need to use the Supabase API (not recommended for seeding), you could use the service role key, but this is more complex and slower. The direct database connection is preferred.

## Important Notes

1. **Stripe Integration**: Update `01_seed_core.sql` with your actual Stripe product and price IDs
2. **User Data**: Seed scripts do NOT create user profiles (these come from auth)
3. **Idempotent**: Scripts use `ON CONFLICT` clauses to be safely re-runnable
4. **Reset Warning**: `00_reset.sql` will delete seed data - use with caution!
5. **Schema Accuracy**: Seed scripts are based on migration files. Use schema discovery to verify column names and types match your database.
6. **Deterministic UUIDs**: All parent records use hardcoded UUIDs for easy reference in dependent seed scripts
7. **RLS Bypass**: Using direct database connection string automatically bypasses RLS - no additional configuration needed
